# 一家 Agent，三套车

## 引子：我先查了一圈，现在有什么

这两周想做的一件事，始于一个很朴素的不满：

> 手上有 DeepSeek、GLM、Kimi 三家的账号甚至订阅，它们各自的"编码 Agent"用起来手感都不一样。但无论是 DeepSeek Harness 里开个自定义 provider，还是在 Cursor / Trae 这种统一的 IDE/CLI 里切换模型，**最后其实都是把模型请求送到当前那一套 agent 框架上跑**——等于让 GLM 去按 DeepSeek 的 prompt 模板、工具协议和思考回路工作，反过来也是一样。

这公平吗？我先翻了一圈，看看市场上和 GitHub 现在都在做什么。

---

## 一、各家都有自己的 "Harness"，而且它远比你想的重要

Yuv.ai 上那篇 _Agent Harness from 0 to 100_ 有个数字非常有名：LangChain 团队把**同一个模型**套进不同的 harness（也就是包裹模型的那层——循环、工具、上下文压缩、执行环境、安全护栏…… 所有模型本身不提供的东西）里去跑 Terminal-Bench 2.0，得分从 **52.8% 跳到 66.5%**，排名一下冲了 25 名。

也就是说：**模型没动一根毫毛，光换一层"外套"，能力就能差一个数量级。**

这不是理论。打开现在的主流产品看一眼就懂：

| 厂商 / 阵营              | Harness / ADE                      | 开源 / 闭源                                                               | 它的模型 + 它自家的框架配合在哪？                                                                                                         |
| ------------------------ | ---------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Anthropic                | **Claude Code**                    | 闭源 CLI                                                                  | 自研的 Tool Schema、Extended Thinking、技能生态、上下文压缩                                                                               |
| OpenAI                   | **Codex Remote / ChatGPT Desktop** | 闭源                                                                      | OpenAI 的 Codex Agent，与 o/GPT 系列深度联调                                                                                              |
| **DeepSeek**             | **DeepSeek Harness (dsh)**         | **MIT 开源**（[GitHub](https://github.com/deepseek-ai/DeepSeek-Harness)） | 插件化、PTC（Programming Thought Chain）编程模式、Markdown Skill + TS 工具                                                                |
| **智谱 / Z.ai**          | **ZCode**                          | **闭源**桌面端（付费）                                                    | 只为 GLM-5.2/5.3 深度适配，"Goals"长任务、飞书/微信/手机远端遥控、ZCode Agent 自研工作流（[官方文档](https://zcode.z.ai/en/docs/agents)） |
| Kimi / 月之暗面          | **KimiCode**                       | 闭源                                                                      | 围绕 Kimi 长上下文和思考强度组织工作流                                                                                                    |
| Google                   | **Antigravity IDE Extensions**     | 闭源                                                                      | 自家 Gemini 与 Google 工程链路打通                                                                                                        |
| Cursor / Windsurf / Trae | 第三方 ADE                         | 闭源/半开源                                                               | 自己写一套 agent 框架，支持用户手动或自动切换模型                                                                                         |

问题就在最后一行——第三方统一框架确实方便，**但它们做的 "多模型支持"，本质是把 A 模型的 API 塞进 "B 风格的 agent loop" 里。**

---

## 二、DeepSeek Harness 是怎么解决"接入其他模型"的？答案：靠一个透明网关

DSH 官方文档给出的路径是：通过 `llm-pi-ai` 插件，在 `settings.yaml` 里写一个 provider block，指向任何 OpenAI 兼容的 endpoint，然后认证写到 `.credentials.yaml`。用 Apidog 那篇文档的话来说：_"harness treats model providers as configuration"_（[Apidog 教程](https://apidog.com/blog/run-any-model-in-deepseek-harness/)）。

这带来的结果很微妙：

- ✅ 能跑。你确实可以在 DSH 里跑 GLM、跑 Gemini、跑本地 Ollama 的 qwen。
- ⚠️ 但**它仍然是在 DeepSeek 的 PTC 模式、DeepSeek 的 Skill 解析、DeepSeek 的插件协议下跑**。

DSH 这种设计已经是业界最友好的了，因为它开源。但放到闭源那边，事情就不那么顺。

**ZCode 是闭源的**——整个桌面 App、多 Agent 编排器、Goals Runtime 全是私有代码，只有 GLM-5.2/5.3 的权重开放（[ZCode 文档](https://ai-tldr.dev/releases/zai-zcode-glm-5-2-jul1/)）。也就是说，如果你想用"官方调教好的、那一套能跨数小时推进软件工程任务的 Goals Agent"，对不起，只能在 ZCode 里面开 GLM。

Kimicode、Codex Remote、Claude Code 的情况，大同小异。

---

## 三、现在的"多模型路由"，都路由在哪一层？

查 GitHub 时我翻了几个典型：

1. **switchboard-llm**：按任务类型（code/reasoning/creative/rag/fast/security）把请求路由到 category 上最合适的模型。bug 修复去 Codestral，200 页文档去 Gemini 1M 上下文，低延迟补全去 Groq。**但它自始至终是同一套应用层在调度**。
2. **agentic**：官方给的方案——在 Claude Code 外面套一层 `ANTHROPIC_BASE_URL` 网关，拦截请求，换任何模型。本质是**让所有模型都假装是 Claude 在被 Claude Code 的 harness 指挥着用**。同 1，外层 harness 没变。
3. **workweave/router**：Anthropic / OpenAI / Gemini 的 drop-in proxy，加了 LLM-classifier 做 tier 路由，和上面一个路数。
4. **adaptive-model-router / llm-use**：把路由放到 agent runtime 内部，根据步骤（planning / tool / coding / summary）选不同模型——更精细，但仍是同一个框架下的"按阶段换模型"。
5. **Harmony Extension** 更进一步：多 Provider 视觉槽位、DeepSwarm 分析 pipeline。但仍然是"多 API 请求 + 统一调度"，不是切到别家 harness。
6. **ACK Gateway Inference Extension**（阿里云 K8s）：更底层，按请求体里 `model:` 字段在后端推理集群之间分流。纯网络层路由，跟 agent 框架没关系。

所有这些都是**"一个 harness + 多模型后端"**。这个思路没有错，能解决 80% 的场景。但它解决不了的是：

> 当 harness 本身的**prompt 模板、工具协议、长任务 loop、UI/工作流/移动端遥控、确认审批流程、Goal 状态机**，这些就是模型能力的一部分的时候，光换 API 后端就是在开自动挡的车跑越野。

而这恰恰是 ZCode / DeepSeek Harness / Claude Code 之间差别最大的那部分。

---

## 四、我想做的东西：不是"一个框架路由多个模型"，是"一个外层路由多个 Harness"

把它形象化一下：

**现在大家都在做：**

```text
用户任务 → 统一的 Agent Loop（Prompt A / Tool A / Flow A）
                ├─ 路由 → DeepSeek API
                ├─ 路由 → GLM API
                └─ 路由 → Kimi API
```

缺点：DeepSeek 那堆 Prompt Template / PTC 模式在跑 GLM；ZCode 那套 Goals 永远走不到。

**我想要的是：**

```text
用户任务 → 中央 Router（做判断 / 做路由 / 做统一接口）
                ├─ 路由 → [ DeepSeek Harness → DeepSeek 模型 ]
                ├─ 路由 → [ ZCode 框架    → GLM 模型     ]
                └─ 路由 → [ KimiCode     → Kimi 模型    ]
                         └─  ↑ 每家自带一整套 agent 循环
```

这就像在一个大公司里设一个总调度台，调度台下面不是"好几个大模型 API"，而是**好几支不同风格、各自装备齐全的工程队**：

- DeepSeek 队擅长插件生态、开源可改、PTC 编程；
- GLM 队擅长跨数小时的长任务 Goals + 手机端遥控 + 国内网络体验；
- Kimi 队处理超长文档 / 多文件上下文；
- 还有通用的 Claude Code / Codex 作为 top-tier 王牌。

**为什么这个方向没怎么有人做？** 因为墙太硬了——

### 墙 1：Harness 闭源 + 体量大

- ZCode 下载安装包几百 MB，启动一堆服务进程，桌面端，带 UI，不是一个 npm 包能 `import` 的事情。
- Codex、Kimicode、Claude Code 同理，要么是桌面 app，要么是 CLI + 长连接服务。

### 墙 2：Skill / Tool / 协议都不兼容

- DeepSeek Harness 是 Markdown Skill + TypeScript Tool，基于 Cordis 插件系统；
- ZCode 有自己的 Skill、Tool Approval、Goal 状态机；
- Claude Code 是独立的 Skill、Context Pack、MCP；
- 中间要转译的东西远不止 HTTP 请求格式，而是"用户授权模型 / 确认指令 / 修改文件 / 执行命令"的完整状态机。

### 墙 3：模型不绑自家 harness，体验就掉一大截

25 名的跳榜故事不是玄学。如果最后 Router 的结果是"把每个任务派到它最适合的那家 harness"，我们真的能把差距补回来吗？**也许正好是反过来：** 既然 harness 差 25 名，为什么不直接用 Router 把任务派到那家 harness？

## 五、Router 怎么路由？四个层次，从傻到聪明

这是我最近一直在想的核心问题——不指望一步到位，分四层来做：

### 第 1 层 · 静态规则路由（MVP 阶段就能跑）

最简单的。用规则 + 元数据先拦住 50% 的情况：

| 条件                                         | 路由到                      | 原因                                  |
| -------------------------------------------- | --------------------------- | ------------------------------------- |
| 明确是"写脚本"类、允许反复试错               | DeepSeek Harness            | 开源可改、PTC 模式适合编码迭代        |
| 任务描述含"长期" / "后台跑" / "等几小时再看" | ZCode (Goals)               | 长程任务 stateful，手机端还能随时打断 |
| 输入材料 PDF / 超长文档 / 百万字规格书       | Kimicode                    | Kimi 长上下文原厂体验                 |
| 涉及 GitHub PR 评审 / 企业私有仓库闭环       | Codex Remote 或 Claude Code | 生态与权限系统更成熟                  |
| 预算敏感 / 离线本地模型                      | DSH + Ollama 适配器         | DSH 可直接挂本地 endpoint             |

就是这么简单。哪怕只是 YAML 一张规则表，也足够有用。

### 第 2 层 · 元数据路由：根据"任务指纹"自动选

给任务抽取几个维度，形成向量或标签，再用一张预定义矩阵：

- **复杂度**：单文件小修改 / 跨模块 / 大型项目
- **自主性**：需要审批每一步 / 允许自由命令 / 最高权限
- **延迟**：30 秒内必须有交互反馈 / 数分钟异步
- **模态**：纯文本 / 含图 / 含浏览器 / 含硬件
- **成本上限**：本次任务预算多少 USD / CNY

类似 Docker 的标签调度，`if cost_cents <= 10 then prefer cheaper harness`。

### 第 3 层 · 轻量分类模型做路由（RouteLLM 式）

这一层就是现在 **switchboard-llm**、**adaptive-model-router**、**agentic auto tier router** 在做的事——用一个小模型（或训练好的分类器）先看一眼任务内容，给出它属于 code / reasoning / creative / rag / research 哪种，再对应路由。

放到"多个 harness"场景下，输出层不再是 10 个 API 模型，而是 3~6 个候选 adapter（DSH、ZCode、Kimicode、Codex……）。

关键：**Router 本身必须是便宜、低延迟、本地能跑的**。别为了路由花掉比任务本身还贵的钱。

### 第 4 层 · 基于历史表现的反馈闭环（Learned Router）

每一条任务跑完，记 5 个数字：

- `harness_id`（跑它的那支队伍）
- `success`（任务结果是否达标，人工或自动打分）
- `cost_usd`（实际消耗，含 API + 订阅时薪摊分）
- `latency_ms`（墙钟耗时）
- `task_embed`（任务向量，做聚类）

过一段时间做一张 "task_category × harness" 的胜率 + 成本表。下次同类任务来，就把路由先让给"性价比最高的那支队伍"。再跑一轮，再喂回来——典型的老虎机 / UCB / 线性贝叶斯路由。

这四层不是谁替代谁，是一层一层叠上去的：

```text
静态规则（100% 命中硬约束）
   ↓ 不命中才走
元数据路由
   ↓
分类器路由（Router LLM）
   ↓ 决策 + 记录
历史反馈闭环（离线学习路由表）
```

## 六、Harness 太大、又闭源怎么办？三种 Adapter 形态

这是最现实的问题。**不可能把 ZCode 整个装进你项目里做一个 import**。我的思路是把 Adapter 分成三种形态：

### 形态 A · 原生嵌入型（开源 harness）

代表：DeepSeek Harness。因为它是 MIT 开源、npm 包、可 programmatic 调用。这种最理想，可以直接打成一个 SDK adapter：

```ts
class DshAdapter implements HarnessAdapter {
  async startTask(task: Task) {
    /* spawn dsh 或直接 import */
  }
  async streamEvents() {
    /* 读事件流 → 统一 schema */
  }
  async approveToolCall(id: string) {
    /* 映射确认 */
  }
}
```

### 形态 B · CLI / Bot 桥接型（闭源但有外部入口）

代表：ZCode（闭源）、Codex CLI、Claude Code。

不要求它被 import，只要它有 CLI、Bot 通道（ZCode 的飞书/微信 Bot 就是现成的）、或 HTTP API。Router 通过 IPC / 子进程 / Webhook 跟它通信：

```text
Central Router
   ├─（本地子进程） →  `codex -p "task..."`    → 读 stdout/stderr 事件
   ├─（飞书 Bot）    →  @ZCodeBot "task..."    → 通过回调收进度
   └─（本地 server） →  dsh 暴露 API            →  正常请求
```

这是闭源 harness 目前最可行的接入方式。

### 形态 C · "透明代理反嵌"型

代表：agentic 项目那种思路。

如果某 harness 允许通过 `BASE_URL / proxy` 来拦截其请求、注入结果，就把 Router 放在它和"模型 API"中间。这样既不修改 harness，也能：

- 观察它内部在做什么；
- 在它请求模型之前先替换成我们想要的那家；
- 收集统计数据喂给 Router 学习层。

这种方式对任何闭源 harness 都能工作，缺点是只能"绕外围"，没法做到 A 形态的任务级控制。

三种形态混着用。一个框架里同时有 A、B、C 三类 adapter 是完全可以的。

## 七、不是"让用户选哪家"，而是"Router 替你选"

这是我最不想回到的旧世界：

```
[下拉框] ▾ 使用模型：
  ├─ DeepSeek-V4
  ├─ GLM-5.3
  ├─ Kimi-Latest
  └─ Claude-Opus
```

用户真的知道在"重构一个老旧的 Python monorepo、后台跑完我去吃饭、中间可能要我审批危险命令"这个任务下，哪个最适合吗？**大多数时候，用户只关心三件事：能做完吗？花多少钱？多久？**

Router 的职责就是把这三件事翻译成"该派哪支队伍上"，然后对用户暴露统一的：

- 输入（自然语言任务描述 + @文件 + 上下文）
- 进度流（现在哪个 harness 在做、做到哪一步、上一步工具调用结果）
- 统一审批界面（要执行 `rm -rf /` 了 → 弹窗，不管背后是谁在喊审批）
- 结果与账单

用户面前永远是一个界面。**Router 下面有多少支工程队，用户不需要知道**——除非他自己想 override。

## 八、挑战与现实

想得很美，现实有几道坎必须老老实实承认：

1. **Harness 协议不统一**。工具调用 schema、approve 请求、context 恢复、error 分类都不一样。要在它们之上再抽一层统一的 Agent 事件总线，工作量不小。
2. **闭源 harness 的稳定性没有保证**。ZCode、Codex 下个版本很可能就改掉 CLI 参数或 Bot 消息格式，B 形态 adapter 会经常坏掉。
3. **成本模型差异大**。DSH 用的是 API Key 按量付费；ZCode 是月订阅；Codex 是账号订阅。如何把"一次任务的成本"统一换算成 USD / CNY 做路由决策，需要单独做账单聚合层。
4. **权限 / 安全**。把同一个工作区、同一套凭据喂给三个 harness，等于三个程序都能修改你的磁盘。必须有独立的沙箱和审批门控。
5. **中间状态迁移**。任务跑到一半，Router 判断"现在这支队伍不行了，该换另一支上"，如何把已经做的修改、已经收集的 tool results、上下文完整迁移？这是最硬的一块，目前我还没有答案——除非你把迁移粒度切到"整段任务跑完才路由"，但那样就失去了中间切队的意义。

---

## 九、结语

回到最开始的矛盾：**同一模型，换 harness 能跳 25 名。那既然大家已经接受"按任务自动路由到不同模型"，为什么不更进一步，按任务自动路由到不同的 harness？**

这个方向上现在能找到的开源实现还不多。agentic、switchboard-llm、router 等都是在"一个 harness 下多模型"的层做得很成熟；**"一个外层下多 harness"** 还没有人认真做——也许是因为闭源门槛高、协议难统一、工程投入大、短期看不见商业回报。

但它是我最近翻完 dsh、ZCode、Codex、agentic、adaptive-model-router、LiteLLM 这一大圈之后最笃定的一个方向：

> Harness 不是外壳。它是模型能力的另一半。既然我们已经在做"模型的模型"（Router LLM），为什么不做"Harness 的 Harness"？

不一定现在就要动手写第一行代码，但这个结构已经在脑子里盘旋太久了——今天把它写下来，也算一个起点。
